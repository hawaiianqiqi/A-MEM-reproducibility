1. Project summary and what I set out to reproduce

A-MEM (Agentic Memory for LLM Agents, arXiv:2502.12110) proposes that an agent's memory should be organised the way a Zettelkasten is: each conversational turn becomes a structured note, notes are linked to their nearest neighbours, and adding a note evolves the notes around it — their context, keywords and tags are rewritten in light of the new arrival. The paper's evidence is LoCoMo, a long-conversation QA benchmark, where A-MEM is reported to roughly double the multi-hop F1 of a full-context baseline (45.85 vs 18.41) while reading an order of magnitude fewer tokens (2,520 vs 16,910 per question).

Target claim (fixed before any run): reproduce the A-MEM column of Table 1 for the GPT-4o-mini backbone — per-category F1 and BLEU-1 on LoCoMo — using the authors' experiment repository WujiangXu/AgenticMemory.

Table 1 of the paper is the right target because it is the paper's headline quantitative claim and because every ingredient needed to check it ships with the code: the LoCoMo file, the evaluation script, the memory implementation and the prompt templates. I deliberately did not use agiresearch/A-mem, the library the paper points practitioners to: its README states that paper results live in the other repository, and it contains no evaluation script, so nothing in it can be checked against a reported number.

Scope. One of the ten released conversations (conversation 0: 419 turns, 199 questions, all five categories present), three trials per arm. The assignment permits reproducing one benchmark or one table row; a single conversation keeps the cost inside a CNY 20 budget while still producing a distribution rather than a single point.

3. Target, metrics, and the measurement decisions that hide inside them

Target. For each of the five LoCoMo categories and for the run as a whole: token-level F1 and BLEU-1 between the predicted answer and the gold answer, in percent.

  • F1 is the harmonic mean of precision and recall over the set of lowercased tokens, after replacing . , ! ? with spaces (utils.simple_tokenize). It rewards content overlap and ignores word order.
  • BLEU-1 is unigram precision with a brevity penalty, computed by nltk.sentence_bleu with weights=(1,0,0,0). It rewards producing the reference's words and punishes padding.

Both are reported as mean ± standard deviation over three trials, where the trials differ only in the answering seed (42/43/44). Memory construction runs once and is cached; later trials re-run retrieval and answering. Variance therefore measures the answering stage, which is where the sampling temperature lives — not memory construction, which the paper never reports. This is a stated limitation, not an oversight: rebuilding the memory three times would triple the cost to estimate a quantity nobody quotes.

Three measurement decisions materially change the numbers, and the report would be dishonest without them:

  1. Category 5 (adversarial) is scored against the wrong answer by default. Category-5 questions have no answer in the conversation — the correct response is "not mentioned". The released harness scores them against "Not mentioned in the conversation", which is right, but the evaluation that produced the paper's Table 1 scored them against adversarial_answer, i.e. the trap. The repository says so in load_dataset.py, and its flag is named legacy_c5. Every run here uses --legacy-c5 so that the comparison is like-for-like; §4 also reports the strict scoring, recomputed from the stored predictions, because the difference is large enough to be a finding in itself.
  2. k. Table 5 of the paper lists k=40 (single-hop, multi-hop, adversarial) and k=50 (temporal, open-domain) for GPT-4o-mini, while the body text says "we primarily employ k=10" and the shipped driver uses 10. This reproduction runs k=10 for all trials and adds a one-trial k=40 sensitivity pass on the same cached memories (§4), so the sensitivity the paper leaves implicit is measured rather than assumed. The k=50 rows and a multi-trial k=40 arm remain unrun for budget reasons.
  3. Dataset size. The paper describes 7,512 QA pairs; the released locomo10.json contains 1,986. The reported numbers were therefore produced on a different, larger instance of the benchmark than the file that ships with the code. Nothing in the repository can close that gap.

One caveat on precision: the standard deviations above are across answer seeds, not across questions. With 13 open-domain questions in this conversation, the sampling error on that category is on the order of ±20 F1 points, so its deviation should be read as "clearly lower", not as a point estimate. The overall figure (30.39) is dominated by single-hop, which contributes 70 of the 199 questions.

Why the gaps are where they are. Single-hop, temporal and open-domain are answered from a single retrieved note; they measure whether the retrieval found the right turn, which is a property of the embedding index rather than of the agentic organisation. DeepSeek is simply a stronger reader than GPT-4o-mini on the single-hop and temporal slices (+17.0, +8.0), and a much more conservative one on open-domain (−34.4): it tends to answer "not mentioned in the conversation" instead of volunteering world knowledge, which is exactly what category 3 punishes. Multi-hop is the one category the paper's thesis actually rests on, and it is the one that did not transfer (−18.5). That is the result worth following up, and §5 follows it up.

The adversarial column is a measurement artefact, in both directions. Scored the paper's way (against the trap answer), A-MEM gets 25.76 here versus 50.03 in the paper. Scored the way the task is actually specified — the correct reply is "not mentioned", so a declining answer is a correct answer — the same predictions score 74.86, with 74% of the 141 answers declining correctly. The paper's 50.03 and this 74.86 describe the same behaviour under two labels. Any leaderboard that puts adversarial F1 next to the other four categories is comparing a similarity-to-a-wrong-answer metric with four similarity-to-a-right-answer metrics.

Retrieval depth is the single largest setting gap, and it is now measured. One extra trial at k=40 — the value Table 5 lists for this backbone — reuses the identical cached memories and differs only in how many notes are retrieved:

Two numbers here are not visible in the paper. First, the write path is 3.1 LLM calls per conversational turn (419 metadata extractions + 892 evolution calls), against 2 calls per question on the read path — building memory costs more calls than answering every question about it. Second, the evolution step inflates the read path too: with links in place, 10 retrieved notes drag their neighbours into the prompt, so one question consumes 11,910 input tokens against 1,508 without evolution — 7.9× — for the same k. A-MEM's selling point is small inference prompts relative to a 16,910-token full-context baseline; at k=10 with neighbour expansion that advantage is 1.4×, not 6.7×, and the mechanism that is supposed to buy it is the one inflating it.

Mean latency is 0.87–0.93 s per call on DeepSeek, so wall clock is dominated by call count, not by model speed. Total spend for the study, read from the provider's balance endpoint rather than from the token estimate: CNY 14.8 (~$2.1) for roughly 6,300 calls, including one discarded build (the run whose BLEU column was broken) and the preflight runs.

5. The change, and what happened to the numbers

The change: disable memory evolution (--no-evolution, one flag, one code path). With the flag set, add_note stores each note with its LLM-extracted metadata but never runs process_memory, so notes never gain links, never strengthen their tags, and never rewrite their neighbours' context. Retrieval, prompts, k, seeds, metrics and the embedding index are untouched. The two arms differ in exactly one mechanism.

This is the right mechanism to isolate because it is the one the paper credits for its largest gain: Table 2 reports multi-hop F1 falling from 45.85 (full) to 31.24 (without memory evolution) to 24.55 (without link generation and evolution). Skipping process_memory removes both, so the arm corresponds to the paper's w/o LG & ME row and predicts a multi-hop drop of roughly 21 F1 points.

Three trials per arm, same questions, same seeds, same prompts; the only difference is whether process_memory runs.

Only one of the five categories moves the way the paper says it should, and it moves a fifth as far. Multi-hop falls from 27.39 to 23.05 (−4.33) where the paper reports −21.30 for the same mechanism removed. The other four categories change by between −1.60 and +3.82, in both directions, which is what noise looks like: over the full question set the arms differ by 0.78 F1 points, against a pooled standard error of 1.6.

This is not a clean refutation, and it should not be read as one. The effect is in the predicted direction on the predicted category, but three trials cannot resolve a 4-point difference when the full arm's own standard deviation on that category is 3.5 points (Welch t ≈ 2.1). A properly powered test of a 4-point effect at that variance needs roughly 8–10 trials per arm, which the remaining budget did not cover. What the data does support is a claim about magnitude: whatever the evolution step contributes here, it is not the 21-point contribution the paper reports.

Why the gap is plausible rather than surprising. The paper's multi-hop gain is measured against a backbone whose full-context baseline collapses on multi-hop questions (LoCoMo 18.41 F1), which suggests GPT-4o-mini struggles to synthesise across retrieved passages on its own. Pre-computing the links — which is what the evolution step does — hands it structure it cannot build. DeepSeek is a stronger multi-hop reader: it reaches 27.39 without that scaffolding, and the same scaffolding then adds very little. If that reading is right, A-MEM's headline number describes an interaction between the mechanism and a specific backbone's weakness, not a property of agentic memory in general.

The mechanism also injects variance. On multi-hop, the full arm's standard deviation is 3.48 against 0.71 without evolution. The evolution step rewrites neighbours' context and tags in place, so a note's retrievability depends on what arrived after it — a nondeterministic process feeding a deterministic metric. That is a cost the paper's single-run reporting cannot show.

What the mechanism costs. Removing it cuts the write path from 1,311 LLM calls to 419 for the same 419 turns — 4.1 calls per turn down to 1.0 — and the build from $0.375 to $0.033, an 11× reduction: the evolution prompts carry five neighbour notes each, so they are both more numerous and longer. Read against the ablation table, the trade is roughly 11× the cost of the entire write path for ~4 F1 points on one of five categories. A practitioner deciding whether to enable evolution should see that ratio before the paper's multi-hop headline.

7. Conclusion

What reproduced. The protocol reproduced end to end: a clean checkout plus a key produces per-category F1 and BLEU-1 on the released data, with the same metric definitions and the same scoring code the paper used, in about 35 minutes on one consumer laptop and one conversation. Within-run variance is small (std 0.3–5.5 F1 points across categories, largest on multi-hop and adversarial), so the harness is stable enough to support an ablation.

What did not reproduce. The absolute numbers, for reasons the assignment explicitly allows and which I have tried to make legible rather than excuse: a different backbone, a smaller evaluation instance than the paper describes (1,986 vs 7,512 questions), and a category-5 scoring convention that inflates the paper's adversarial column. Retrieval depth — the other obvious setting gap — was measured, not excused: at k=40 it recovers 9 of the missing points overall and most of the adversarial gap, but leaves multi-hop and open-domain essentially unmoved, so the model and dataset remain the best explanations for those two. More substantively, the paper's structural claim — that removing link generation and memory evolution costs about 21 multi-hop F1 points — does not hold at that magnitude here: the same removal costs 4.33 points, in the predicted direction, on the predicted category, but only a fifth of the size, and not separable from noise at three trials. On this backbone the mechanism is real but small, and it is priced at 11× the cost of the write path it modifies.

The honest summary of the ablation is therefore that it is inconclusive in the direction the assignment cares about. It is not a failed reproduction: the direction matched, the cost effect was large and clean, and the variance effect (3.48 vs 0.71 on multi-hop) was not something I expected. But a 3-trial test of a 4-point effect at that variance cannot support a claim either way, and I would rather report the confidence interval than the point estimate.

What is worth reporting even if it "failed". Three of the findings here are not about A-MEM at all; they are about the practice of reproducing agentic systems. A cache path that omits the configuration silently turns an ablation into a no-op. A swallowed exception turns a broken metric into a table of zeros that reads like a low score. A scoring convention that scores against the wrong answer turns a failure mode into a headline number. Each of these would have been invisible in a single-run report, and each was found only because the numbers were reported as a distribution and checked against a second convention.

Remaining unfinished items. The k=40 sensitivity pass is one trial, so its per-category cells carry no variance estimate (the k=10 baseline's own std bounds suggest the adversarial and temporal gains are real, but the multi-hop +2.5 is within noise). The k=50 rows, the ablation arm at k=40, and a multi-trial k=40 would each cost another answering trial at roughly four times the k=10 rate; the harness supports all three (bash run_repro.sh k40), and the memory caches are reusable, so they are a 30-minute job each for anyone with the budget. Reporting one k at one trial per sensitivity cell is a limitation of this submission, not a property of the method.

Advice to the next person. Run the environment preflight before anything else; freeze the target claim in writing before the first paid call; isolate the ablation cache on day one; and print the metric definition's edge cases (empty prediction, category-5 reference, int vs str answers) next to the first result, because every one of those was silently wrong here before it was caught.
